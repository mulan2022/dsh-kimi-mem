# Kimi 聊天记忆导入与真实样本对比

核对日期：2026-10-30。样本是工作区里的 `kimi_memory_vault/`；本报告不把导出文件里的指令当成本次操作指令。没有联网验证 Kimi 服务端实现，下面区分文件证据、日志自述和推断。

## 首版导入怎么用

重新加载构建后的插件，在「设置 → 记忆空间 → 聊天记忆 → 导入 Kimi 记忆库」填写运行 DSH 那台电脑上的解压目录，点击「备份并覆盖导入」。这是本机目录导入，当前不支持浏览器上传 ZIP。

**只替换 `<DSH home>/.dsh-mem/spaces/chat/`。** Kimi 里提到的个人项目仍是聊天中的实体，不会按名称拆进项目库。

以下内容保持原样：

- `shared/`：常驻记忆和全局共用内容。
- `spaces/project/`：所有项目分区、实体和时间线。
- 全局 `raw/turns/`、工作区登记表、历史回填账本与 DSH 官方会话。
- 索引中的 shared/project 条目与 sessions 记录。

旧聊天库备份到 `.dsh-mem/backups/kimi-<时间戳与随机号>/chat/`。导入失败会尝试回滚文件替换与索引事务。整理运行中拒绝导入；不要同时启动另一个共享同一 home 的 DSH 进程写库。

导入后新建一个「聊天模式」会话使用；已有会话中注入的旧记忆快照不会被追溯替换。shared 原有信息仍会按原来的规则加载，导入不会自动消除它与聊天库之间的冲突。

也可以在插件目录使用：

```powershell
# 先关闭使用同一个 home 的 DSH，再执行离线导入。
npm run import:kimi -- D:/demo/MemoryChat/kimi_memory_vault --preview
npm run import:kimi -- D:/demo/MemoryChat/kimi_memory_vault

# 配置了自定义 home 时须明确指定相同路径。
npm run import:kimi -- D:/demo/MemoryChat/kimi_memory_vault --home D:/your-dsh-home
```

Windows 双击 `scripts/import-kimi.cmd`，或把解压后的目录拖到它上面。npm 安装包也提供 `dsh-mem-import-kimi` 命令。默认 home 为 `DSH_HOME`，未设置则为 `~/.dsh`；网页入口直接使用插件当前配置的 home。

## 已按 Kimi 兼容的部分

1. **分节格式与名称。** 原生解析 Kimi 的 `path/title`，按文件顺序读取，默认作为 resident 分节；仍兼容旧的 `file/name/resident/order`。新建聊天库模板采用 `personal_context.md`、`work_context.md`、`this_month.md`、`earlier_months.md`、`taste.md`、`memory_tips.md`。初始化读取已有配置，不再根据新模板给旧库乱补分节。
2. **保留 canonical。** 分节、实体、observations、日志和附件保留原始内容与目录，不把实体拆成原子事实，也不按内容搬进项目库。没有把用户的个人数据写入源码模板或测试夹具。
3. **重建派生文件。** README 与日志有明确的截断标记，README 的内容与 canonical 分节也不完全一致；因此从配置里的六份分节重建 README，从全部分节和实体重建 index。原版 README、index 和配置另存到 `raw/kimi-original/`。这保证正文完整性，但不声称复刻了 Kimi 未公开的 README 合成算法。
4. **链接兼容。** 支持 `[[路径|显示名]]` 的显示和页面跳转，实体一跳查询也识别 `entities/xxx` 目标。附件文件与引用路径原样保留；图片内嵌预览不是这次的完整实现。
5. **来源编号不冒充本地聊天。** 保留 `[^N]`，为已出现的编号建立 `kimi-import` 来源记录，明确 `originalAvailable: false`，不编造 DSH session、turn、时间；后续本地锚点从最大编号之后继续分配。附件的 source_ref 元数据不能替代完整对话。
6. **修复实体的会话隔离。** 公共实体索引现在仅含 shared；聊天实体只在聊天会话参与目录与自动召回，`mem_entity` 也只查 shared + 当前空间，避免导入后串入项目上下文。显式跨空间搜索工具的既有能力不变。
7. **只刷新聊天索引。** 覆盖后删除聊天索引的旧条目、索引新文件，并刷新实体缓存；shared/project 的索引条目不变。
8. **提取提示词。** 聊天 observations 定义为模型对用户行为方式的有价值总结，要求保留情境、行为证据、推断边界和反例。解释不必等用户逐字确认，但不能冒充用户自述。无重要性或无解释价值的内容留在原始轮次，经 RCC / BM25 按需召回，不送入 observations 暂存。这是规则调整，尚未用模型端到端验证产出改善。

## 仍然不同、值得接着改的部分

| 差异 | 证据与判断 | 建议顺序 |
| --- | --- | --- |
| 实体产出与关系覆盖 | Kimi 的 90 页覆盖人物、工具、组织、事件、价值观和项目，并解释“它与用户的关系”。本地聊天实体目前为空；我们的 merge 提示词已经要求建实体，单纯再加同一句提示词不够。 | P0：用固定聊天样本走完整理链路，检查提名 → merge → 实际落盘每一步。 |
| 记忆写作深度 | Kimi 的正文大量保留“触发情境 → 用户反应 → 什么回应有效 → 是否再次印证”，而本地样本更多是事实、状态和偏好的罗列。这是产物观察，不是对其内部提示词的确认。 | 已调整规则：observations 只保存有价值的行为观察，置信度与重要性分开；有揭示性的单次互动也可入选，无价值碎屑留原始素材，不以“暂存”兜底。仍需端到端评估。 |
| 健康检查 | Kimi `log.md` 多次自述 orphan、未解析双链、README 超预算和修复过程；导出实体页仍有两个未解析的非 raw 链接目标，说明不能把日志里的 healthy 当完整证明。dsh 当前主要依赖整理模型自报 health。 | P1：代码检查孤立实体、缺失目标、来源、分节预算和 README 一致性，给出可定位报告。 |
| 6000 字预算 | Kimi 配置有 `inject_char_cap: 6000`；六节实际共 7,236 字符，日志也把预算作为健康问题处理。不能由这个配置断定生产环境会怎样裁切。 | 首版保留该目标并在导入报告里标出超限；不机械截掉后半段。dsh 运行时仍受现有 `injectMaxChars` 总预算限制。下一步做整理时压缩与分节预算。 |
| 月份归档 | 样本有 `sections/archived_month/YYYY-MM/this_month.md`，同时有 `earlier_months.md`；dsh 原有滚动依赖显式 `window` 和 `## YYYY-MM`，归档到一个文件。Kimi 配置没有 window，本月正文也没有这一标题。 | P2：专门实现 native schema 的月切换和摘要压缩；此次保留导出目录，不添加猜测的月份，也不宣称已自动滚动。新建模板保留 window 扩展，继续支持带日期标题的旧滚动算法；导入文件保持 Kimi 原配置，不擅自添加 window。 |
| 附件归属 | Kimi 将少量附件实际放进 vault，并有 `.meta.json`；dsh 后续采集仍主要存官方附件库路径。 | P2：有选择地复制耐久工件，给附件增加来源与可用性检查；导入附件本次已完整保留。 |
| 自动整理 | Kimi 日志体现多次 ingest、worker、汇总与健康修复，但只凭导出无法确认精确调度频率。dsh 已于 2026-11-02 接通无人值守路径：进程运行时按配置时间及空闲条件自动执行，无活会话时使用后台子会话。 | 已增加自动接线、失败重试、锁与记账测试；真实模型的完整整理效果仍需运行验收。 |

## 不能从这份导出证实的机制

RCC 的真实窗口、截断参数、线上检索排序、渐进注入、身份匹配和会话锁定，都不能由静态 vault 单独证明。实体页中关于这些机制的讨论是历史聊天的整理记录，不等于生产代码或协议。现有 RCC 实现保留；不把导出的 85 个 source_ref 伪造成 85 场本地对话。

## 验证范围

构建、TypeScript 检查、现有宿主与客户端冒烟测试，以及新增的隔离导入测试。新增测试检查覆盖清理、旧库备份、shared/project 文件与索引不变、原始轮次和会话记录不变、来源编号延续、二进制一致性、双链一跳、索引失败后回滚、越界源路径拒绝及 HTTP 导入请求校验。

另用这份真实导出在临时 home 完成导入，核对 90 个实体和六份 canonical 分节可读，聊天索引重建。没有覆盖正式聊天库；网页的完整交互尚未在真实运行的 DSH 浏览器中手工验收。

## 2026-11-02：整理按会话空间单路执行

dream 每个会话仅派一个提取者，沿用 preset / 工作区判定；聊天和各项目按目标 vault 分别汇总，串行写入。历史会话优先使用官方日志中的 preset 元数据，新采集轮次保存 preset；不再按内容向两个空间各提取一遍。已验证项目目录中的 chat preset 不误入项目库，两个项目的同号来源锚点也分别校验。
